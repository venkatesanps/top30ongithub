How a Snowflake query runs

From the moment you press Run to the rows on your screen: what happens in cloud services, when a warehouse is needed at all, how micro-partitions get skipped, and where the credits go. Press play, or pick a scenario to see a different route.

1Authenticate and check access

Cloud services checks who you are and what your role may read: row access and masking policies are applied to the plan here, before any data moves.

Costs
Cloud services credits, billed only above 10% of the day's warehouse credits
Check
LOGIN_HISTORY, role grants

2Parse, optimize, compile

The optimizer picks join order and methods and prunes at compile time: each micro-partition's min/max metadata says whether it can hold matching rows. EXPLAIN shows this plan without running anything, and needs no warehouse.

Read it
EXPLAIN USING JSON <query>: partitionsAssigned of partitionsTotal
Watch for
Compile time in seconds: very large IN lists, deep views, thousands of UNION branches

3Result cache hit: no warehouse

A result is kept 24 hours, and every reuse resets the clock, up to 31 days from the first run. Reuse needs the same query text (case and aliases count), unchanged data and micro-partitions, access to every table, no per-run functions such as RANDOM or UUID_STRING, no external functions or hybrid tables, and USE_CACHED_RESULT on. Even then, reuse isn't guaranteed.

Costs
No warehouse credits
Helps
BI tools that send identical SQL; stable formatting in generated queries

4Answer from metadata no warehouse

Some simple aggregates, such as SELECT COUNT(*) FROM t, come straight from the metadata Snowflake keeps for every micro-partition. Query Profile shows a metadata-based result.

5Resume or queue the warehouse compute starts

A suspended warehouse resumes first: billing is per second with a 60-second minimum each time it starts. A busy one queues the query; multi-cluster warehouses (Enterprise edition) add clusters for many users, which helps concurrency, not a single slow query. Query Acceleration can lease extra compute for big eligible scans, capped by a scale factor.

Check
QUERY_HISTORY: QUEUED_OVERLOAD_TIME, QUEUED_PROVISIONING_TIME
Check
SHOW WAREHOUSES: generation, enable_query_acceleration

6Scan: fewer partitions, fewer columns

Each node reads its share of the assigned micro-partitions, only the columns the query uses. Runtime pruning skips more, for example partitions a join filter rules out. Data already on the warehouse's SSD cache is read locally; the rest comes from remote storage. The cache is dropped when the warehouse suspends.

Good sign
Partitions scanned far below total; high "percentage scanned from cache"
Prunes badly
Functions or casts on the filtered column, filters on columns the data isn't ordered by, leading-wildcard LIKE

7Execute in parallel, spill if needed

The plan runs on every node of the warehouse at once. When an operator outgrows memory it spills to local SSD, then to remote storage. Remote spill is the slow, expensive case: shrink the work first (filter earlier, fewer columns, fix exploding joins), then try a bigger warehouse.

Read it
GET_QUERY_OPERATOR_STATS(LAST_QUERY_ID()): rows in vs out, spilling, time per operator
Exploding join
A join with more output rows than input rows

8Return results, keep them for next time

Rows stream back to you and the result is persisted, so the same query within 24 hours can skip all of the above. The warehouse keeps billing until it auto-suspends.

Tune
AUTO_SUSPEND: short for ETL; a few minutes for BI keeps the SSD cache warm

What a warehouse costs per hour

Credits per hour while running, billed per second with a 60-second minimum per start. Gen2 is the default for new standard warehouses where available; existing warehouses keep their generation. Gen2 isn't offered at 5XL or 6XL. Size up doubles the rate; it pays off only when the query finishes more than twice as fast.

SizeGen1Gen2 AWS, GCPGen2 Azure

Cloud services (compiling, metadata, the result cache) are billed only for the part above 10% of each day's warehouse credits, in UTC.
